1 Resumen ejecutivo

El Hito M3.5 introduce un chatbot inteligente integrado en el dashboard que actúa como un analista de ciberseguridad virtual, capaz de:

  • Consultar datos históricos y en tiempo real usando lenguaje natural.
  • Explicar eventos, alertas y métricas técnicas en términos comprensibles.
  • Recomendar acciones de remediación basadas en el contexto específico del tenant.
  • Correlacionar eventos dispersos para identificar patrones de ataque.

Este chatbot transforma SC-Sentinel de una herramienta de monitoreo pasivo a un asistente proactivo de seguridad, reduciendo la barrera de entrada para usuarios no técnicos y acelerando el tiempo de respuesta ante incidentes.

💼 Valor de negocio

  • Diferenciación competitiva: pocos productos de monitoreo ofrecen un asistente conversacional especializado.
  • Reducción de tiempo de triage: analiza horas de logs en segundos.
  • Educación continua: explica conceptos de ciberseguridad en contexto real.
  • Casos de uso expandidos: desde SOC analista hasta auditoría conversacional.

2 Objetivos del hito

2.1 Objetivos funcionales

  • F1: Chat UI integrado en el dashboard (widget flotante o página dedicada).
  • F2: Consultas en lenguaje natural sobre eventos de red (ej. “¿Qué IPs me atacaron ayer?”).
  • F3: Explicación de alertas en términos comprensibles (ej. “¿Qué significa 'TCP SYN flood'?”).
  • F4: Recomendaciones de remediación basadas en el contexto del tenant.
  • F5: Correlación de eventos históricos (ej. “¿Este IP apareció en ataques anteriores?”).
  • F6: Análisis de tendencias (ej. “¿El tráfico ha aumentado en la última semana?”).
  • F7: Memoria de contexto conversacional (recordar preguntas previas en la sesión).
  • F8: Streaming de respuestas (UX fluida, no esperar al texto completo).
  • F9: Exportación de conversaciones a reportes (PDF/Markdown).
  • F10: Modo “incident response” guiado (workflow paso a paso).
  • F11: Auditoría conversacional (quién preguntó qué y cuándo).
  • F12: Sugerencias contextuales (botones de preguntas frecuentes relevantes).

2.2 Objetivos no funcionales

IDObjetivoMétrica
NF1Latencia de primera respuesta< 2 segundos (streaming)
NF2Precisión< 5% de hallucinations
NF3SeguridadSolo admins autenticados
NF4PrivacidadConversaciones no salen del tenant
NF5Costo< 2000 tokens por consulta (promedio)
NF6Escalabilidad100 conversaciones simultáneas
NF7ObservabilidadLogs de consultas y métricas de uso
NF8AccesibilidadWCAG 2.1 AA

2.3 Fuera de alcance (explícitamente NO entra en M3.5)

  • ❌ Entrenamiento de modelos personalizados (usamos LLMs pre-entrenados con RAG).
  • ❌ Ejecución automática de acciones (solo recomendaciones, no cambios en el sistema).
  • ❌ Integración con herramientas externas (VirusTotal, Shodan) — queda para M6+.
  • ❌ Soporte multi-tenant en el chat (cada tenant tiene su propio contexto aislado).
  • ❌ Voz (solo texto por ahora).

4 Arquitectura técnica

4.1 Componentes del sistema

01
Frontend (Next.js)
ChatWidget flotante o página /dashboard/chat. Input de texto, streaming de respuestas, sugerencias contextuales, historial de conversaciones.
02
API Routes (Next.js)
POST /api/chat (autenticación + streaming SSE + orquestación). GET /api/chat/history (recuperar conversaciones).
03
Chat Pipeline (lib/chat/)
Context Builder → Query Classifier → RAG → LLM Call → Response Validator.
04
Database (Neon PostgreSQL)
Tablas chat_conversations y chat_messages para persistencia y auditoría.

4.2 Decisiones de diseño (ADRs)

IDDecisiónJustificación
ADR-M3.5-01RAG con consultas SQL directas (no vector DB)Simplicidad, latencia baja, datos ya estructurados en Neon. Vector DB queda para M6+.
ADR-M3.5-02Streaming con Server-Sent Events (SSE)UX fluida, compatible con Next.js, no requiere WebSockets.
ADR-M3.5-03System prompt especializado por tenantContexto específico (dispositivos, alertas, configuración) mejora precisión.
ADR-M3.5-04Límite de contexto: últimas 10 conversacionesEvita enviar demasiado contexto al LLM (costo y latencia).
ADR-M3.5-05Validación de hallucinations con queries SQLSi el LLM menciona un IP, verificar que existe en la DB antes de mostrarlo.
ADR-M3.5-06Solo admins pueden usar el chatSeguridad: el chat tiene acceso a datos sensibles del tenant.
ADR-M3.5-07Persistencia de conversaciones en NeonAuditoría, continuidad de contexto, exportación.
ADR-M3.5-08Sin ejecución automática de accionesSeguridad: el chatbot solo recomienda, no ejecuta cambios.

4.3 Flujo de una consulta típica

01
POST /api/chat
Autenticación con verifyAdminAuth. Body: { message: “¿Qué IPs me atacaron ayer?”, conversation_id: “conv_123” }
02
Context Builder
Recuperar últimas 10 conversaciones de conv_123. Recuperar alertas de ayer y top hosts. Construir contexto: “Ayer hubo 47 alertas, top 3 IPs: 192.168.1.100, 10.0.0.5, 172.16.0.1”
03
Query Classifier
Intención: “listar IPs maliciosos”. Entidades: fecha=“ayer”. Tipo de query: SQL directa a alerts + host_stats.
04
RAG (consultas SQL)
Query 1: SELECT DISTINCT host_key FROM host_stats WHERE risk_score='high' AND window_id IN (...). Query 2: SELECT COUNT(*) FROM alerts WHERE created_at > NOW() - INTERVAL '1 day'. Resultado: 3 IPs, 47 alertas.
05
LLM Call (Groq/Gemini)
System prompt especializado + contexto + pregunta. Streaming de respuesta vía SSE.
06
Response Validator
Validar que los IPs mencionados existen en la DB. Formatear markdown. Persistir en chat_messages.
07
Respuesta al usuario (streaming)
“Ayer detecté 3 IPs que te atacaron: 192.168.1.100 (23 alertas, SYN flood), 10.0.0.5 (15 alertas, port scan), 172.16.0.1 (9 alertas, blacklist hit). ¿Quieres que te explique cómo mitigarlo?”

4.4 Esquema de base de datos (Migración 0005)

CREATE TABLE chat_conversations (
  id TEXT PRIMARY KEY,
  device_id TEXT NOT NULL REFERENCES devices(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  metadata JSONB DEFAULT '{}'::jsonb
);

CREATE TABLE chat_messages (
  id TEXT PRIMARY KEY,
  conversation_id TEXT NOT NULL
    REFERENCES chat_conversations(id) ON DELETE CASCADE,
  role TEXT NOT NULL CHECK (role IN ('user','assistant','system')),
  content TEXT NOT NULL,
  tokens_used INTEGER DEFAULT 0,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX chat_messages_conversation_idx
  ON chat_messages(conversation_id);
CREATE INDEX chat_messages_created_at_idx
  ON chat_messages(created_at);

Query Classifier

  • “¿Qué hago si detecto un ataque?” → intención=recomendar.

RAG

  • Intención=listar IPs → genera query SQL correcta.
  • Intención=explicar → no genera query (usa knowledge base).

Validator

  • Respuesta con IP inventada → warning.
  • Respuesta sin IPs → OK (no valida).

LLM

  • System prompt incluye contexto del tenant.
  • Streaming funciona (SSE chunks).
  • Error de API → manejo controlado.

12 Anexo: Queries SQL generadas por RAG

Consulta: “¿Qué IPs me atacaron ayer?”

SELECT DISTINCT host_key, COUNT(*) as alert_count
FROM alerts
WHERE created_at > NOW() - INTERVAL '1 day'
  AND severity IN ('high', 'critical')
GROUP BY host_key
ORDER BY alert_count DESC
LIMIT 10;

Consulta: “¿Hubo ataques la semana pasada?”

SELECT DATE(created_at) as date, COUNT(*) as alert_count
FROM alerts
WHERE created_at > NOW() - INTERVAL '7 days'
GROUP BY DATE(created_at)
ORDER BY date;

Consulta: “¿Qué puertos están más expuestos?”

SELECT dst_port, COUNT(*) as connection_count
FROM flow_windows
WHERE start_at > NOW() - INTERVAL '1 day'
GROUP BY dst_port
ORDER BY connection_count DESC
LIMIT 10;
